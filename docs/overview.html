Overview

From a client's request to a draft engagement letter, with a partner in charge

A multi-agent system for SB&P, a Kuwaiti audit and advisory firm with 45 services across nine service lines. A prospective client describes what they need in their own words; the system works out which services apply, drafts the engagement letter, and stops at partner review. Nothing reaches a client without a partner.

It runs fully locally (Ollama), with three agents, an MCP server for every database action, retrieval over the firm's catalog, and checks in plain code at every step.

All client data is invented. Use the buttons below or the arrow keys.

The problem

The hard part is restraint

Some requests fall outside the firm's services. A model answering from memory maps them onto whichever service sounds closest, and writes a confident letter for the wrong work.

"We need someone to represent us before the commercial court, review and redraft our supplier contracts, and advise us on our legal position."
A request for a law firm, not an audit firm.

In the course's first week, on a simple triage task, 4 of 5 prompting approaches selected services the client never asked for. So the system must be able to say "not us", and hand unclear cases to a human.

How it works

One pipeline, routed by code

Blue: agents (LLMs). Grey: plain code. Pink: people. Any failed check, an unclear verdict, or a disagreement that survives the debate goes to the partner queue. No model decides where a case goes.

Patterns: ReAct inside triage (the model chooses its own tool calls) · plan, then execute in the checker (it lists the needs; code runs one search per need) · draft, critique, redraft for the letter · debate between triage and checker · and around it all, handoffs routed by code (a LangGraph graph).

The agents

Three agents, each with a narrow job

Triage

gemma4:12b · local

Finds the client, splits the request into needs, searches the catalog once per need.

Writes the scope memo: each service with the client's own words, what was ruled out, what the firm doesn't offer.

Checker

qwen3.5:9b · local (optional: Claude)

Works out its own answer from the same request, without seeing triage's.

Code compares the two; if they disagree in a way that matters, they debate. Later it reads the letter.

Drafter

gemma4:12b · local

Writes the client-specific parts of the letter from the approved memo only, never the client's raw text.

Code adds the fixed parts: "draft" banner, fee placeholder, standard terms.

All database access goes through one MCP server with six tools, and each agent gets only the tools its role needs. Catalog search is retrieval over the firm's own service descriptions (embeddings, minimum similarity 0.33).

One case, end to end

Record 1: an existing client

"…our bank has now asked for audited statements as a condition for renewing our credit facility… We also need our zakat declaration prepared and filed…"
  1. Triage finds client 1, searches each need, selects AUD-001 Financial Statement Audit and TAX-002 Zakat Declaration, each with the client's sentence.
  2. Memo checks: both services exist, are active, and their quotes really appear in the request.
  3. Checker, on its own, reaches the same two services → agree → drafting.
  4. Drafter writes the letter; code checks it; the checker reads it (it once caught the letter implying the bank would renew the facility, so it was redrafted).
  5. Saved as pending review. The partner sees each service next to the client's words, and approves.

About 80 seconds on local models.

Safeguards

Safety doesn't depend on a prompt being obeyed

DefenceIn the pipeline
Least privilegeNo agent can approve, send, or change a status. The drafter has no tools.
Checks on what a tool acceptsSaving a draft rejects unknown or paused services; agents can't call tools outside their list.
Consequential actions behind code or a humanRouting is code; drafts are saved only as pending review; only a partner changes a status.
The model never carries critical valuesClient IDs come from tool results, not the model (a test run once put a prospect's ID into the client field).
Untrusted text is kept awayThe drafter sees the approved memo, never the client's raw text.
Checks at every boundaryInput shape · "no quote, no service" · letter: approved services only, no money, no other client's name.

Code checks the route, the services, safety (nothing approved or sent, no other client named) and the steps taken. Letter quality is scored 1–5 by a judge from a different model family; I graded the same letters myself and 10 of 12 scores were within one point. Scope accuracy and tone score 5; completeness rose from 2–3 to 3–4 after making the client's responsibilities specific to each service.

Honest limits, and what's next

Limits

  • Small, self-written test set; one run per case.
  • Input checks can't detect a hidden instruction; the structure has to stop it.
  • It matches what clients ask for, not their underlying problems; that's the partner's job.
  • No client history: a renewal looks like a new request.
  • Strict checks can make letters less useful.

Next

  • A learning agent: partners' corrections become house rules.
  • More document types (client emails, reports).
  • The pipeline as an MCP server, usable from Claude.
  • Attack variants generated in volume; monitoring in use.
